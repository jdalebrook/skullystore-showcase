# SkullyStore — guía de trabajo

Tienda online a medida. Contexto de negocio y decisiones de producto en [ROADMAP.md](./ROADMAP.md); instrucciones de puesta en marcha en [README.md](./README.md). Este archivo es para quien (persona o agente) vaya a tocar código.

## Decisiones de arquitectura que no son obvias

- **Next.js 16 renombró `middleware.ts` a `proxy.ts`** (mismo comportamiento, nuevo nombre de archivo/export). Este proyecto usa `src/proxy.ts`. No crear un `middleware.ts` — no se ejecutaría.
- **Prisma 7 requiere un driver adapter explícito.** No basta con `new PrismaClient()`; hay que pasar `adapter: new PrismaPg({ connectionString: ... })` (ver `src/lib/prisma.ts`). El cliente generado vive en `src/generated/prisma` (no en `@prisma/client` directamente) y no se versiona — se regenera con `npx prisma generate` (lo hace automáticamente `migrate dev` y `db seed`).
- **shadcn/ui aquí usa Base UI, no Radix.** Los componentes en `src/components/ui/` importan de `@base-ui/react/*`. Diferencias prácticas frente a Radix: para renderizar un `Button` como otro elemento (ej. un `<Link>`) se usa la prop `render={<Link .../>}` en vez de `asChild`, y si el elemento renderizado no es un `<button>` nativo hay que añadir `nativeButton={false}` o Base UI avisa en consola.
- **`params` y `searchParams` son `Promise`** en las páginas (`await params`), como en versiones recientes de Next — no ha cambiado respecto a lo habitual, pero conviene no dar por hecho lo contrario.
- **Auth.js v5 con Credentials usa estrategia JWT**, no sesiones en base de datos (Credentials + adapter de BD no encajan bien). El rol (`CUSTOMER` / `ADMIN`) viaja en el JWT (`src/lib/auth.ts`, callbacks `jwt`/`session`).
- **`src/lib/site-config.ts` centraliza la identidad de la tienda** (nombre, descripción, dominio, email de contacto, moneda/locale, ruta del logo, datos legales del titular) -- pensado para cuando se clone este proyecto como base de otra tienda (mismo dueño, otro nicho): rellenar de nuevo `siteConfig` es la única fuente de verdad, en vez de buscar "SkullyStore"/el NIF/el email a mano por ~15 archivos (título/metadata, cabecera, footer, las 4 páginas legales, asuntos y remitente de los emails). **No cubre** moneda de verdad (el `currency=EUR` fijo en la URL del SDK de PayPal y los rótulos "(€)" del formulario de producto siguen fijos -- cambiar de moneda implica revisar todo el flujo de precios/PayPal, no solo textos) ni el favicon (`src/app/favicon.ico`, archivo binario, no código). El modelo de clonado es "una instancia Docker independiente por tienda" (ver `deploy/RUNBOOK.md` → "Primera vez"), no multi-tenant real -- decisión tomada con el usuario dado el bajo volumen esperado de clones (1-2 al año) y que él mismo gestiona todas las tiendas.
- **Carrito de dos niveles**: mientras el usuario no ha entrado en checkout, el carrito vive solo en `localStorage` (`src/components/cart-provider.tsx`). Al pulsar "Finalizar compra" se sincroniza con la tabla `Cart`/`CartItem` (`syncServerCart`, Fase 5→7) y desde ahí el checkout usa siempre datos y precios leídos de servidor, nunca los que mande el cliente.
- **Borrar un producto (`deleteProduct`) distingue `CartItem` de `OrderItem`**: `CartItem.product` tiene `onDelete: Cascade` (si el producto desaparece, que desaparezca también de cualquier carrito, no tiene valor histórico) pero `OrderItem.product` no lo tiene a propósito — un pedido ya hecho tiene que conservar su historial aunque el producto deje de venderse. Por eso `deleteProduct` comprueba `prisma.orderItem.count()` *antes* de intentar el borrado y lanza un error legible si el producto tiene pedidos, en vez de dejar que Postgres lo rechace con una violación de FK sin explicación (mismo patrón que `deleteCategory` en `categories.ts`, que ya hacía esto para categorías con productos). El único camino para "quitar" un producto con historial de pedidos es desactivarlo (`isActive`/interruptor "Visible"), no borrarlo. Al borrar un producto sin pedidos, también se borran sus imágenes del disco (`deleteImageFiles`) para no dejar archivos huérfanos.
- **Imágenes de producto se guardan en disco local**, no en un bucket externo (`src/lib/storage.ts`) desde `ImageUploader` (`src/components/admin/image-uploader.tsx`) → `POST /api/admin/upload`. Se descartó Cloudflare R2 tras probarlo: con un volumen de ~100 imágenes no compensaba depender de una cuenta externa ni exponer un dominio público tipo `pub-*.r2.dev`. El campo sigue siendo una lista de URLs separadas por salto de línea por debajo (`imageUrls`, un `<input type="hidden">` que rellena el uploader) — `parseImageUrls` en `src/lib/actions/admin/products.ts` no cambió, y se puede seguir pegando una URL externa a mano si se prefiere.
- **Las imágenes NO viven en `public/uploads/`, viven en `/app/uploads/` (fuera de `public`) y se sirven con una ruta dinámica** (`src/app/uploads/[filename]/route.ts`), no como estático de Next. Esto costó un bug real en producción: el servidor standalone de Next.js calcula la lista de archivos de `public/` al arrancar, así que un archivo escrito ahí en caliente (una subida nueva) no se servía — daba 404 — hasta el siguiente `docker compose restart`. Se confirmó en vivo: el archivo ya estaba en el volumen con los permisos correctos, pero `GET /uploads/<archivo>` daba 404 con cabeceras de página-no-encontrada de Next, y pasaba a 200 justo después de un restart sin ningún cambio de código. La ruta dinámica lee el archivo del disco en cada petición (`readFile`), así que no tiene ese problema — a cambio de perder el `Cache-Control` automático de los estáticos de Next, por eso `route.ts` fija uno a mano (`public, max-age=31536000, immutable`, seguro porque el nombre incluye un UUID: un archivo con esa URL nunca cambia de contenido). Si se necesita cualquier otro directorio escribible en caliente en producción (no solo imágenes), aplica la misma limitación — no uses `public/` para eso.
- **En producción, `/app/uploads` es un volumen Docker aparte** (`skullystore_uploads` en `docker-compose.prod.yml`) para que sobreviva a los rebuilds de la imagen `app` en cada deploy — sin ese volumen, las imágenes subidas se perderían en el siguiente `docker compose up --build`.
- **Las miniaturas del uploader usan `<img>` normal, no `next/image`**: una URL pegada a mano puede ser de cualquier dominio, y `next/image` exige que el dominio esté en `remotePatterns`. Es solo para la vista previa del admin — el escaparate público sí usa `next/image` (`ProductCard`, el modal de detalle, `CartDrawer`), pero como las imágenes subidas son same-origin (`/uploads/...`) no hace falta tocar `remotePatterns` ni la CSP para ellas; solo dominios externos pegados a mano (ej. `picsum.photos` en desarrollo) necesitan estar allí.
- **Las imágenes de `/uploads/...` se pasan con `unoptimized` a `next/image`** en `ProductCard`/`ProductDetailModal`/`CartDrawer`. Otro bug real en producción: el optimizador de `next/image` (`/_next/image?url=...`), para una URL local (que no empieza por `http`), intenta leer el archivo directamente del disco asumiendo que vive bajo `public/` — y como las imágenes subidas viven fuera de `public/` a propósito (ver el punto de arriba sobre `uploads/`), esa lectura fallaba con `400 Bad Request` en vez de servir la miniatura. No hacía falta arreglarlo de otra forma: `uploadProductImage()` ya redimensiona (máx. 1600px) y comprime a WebP en el momento de subir la imagen, así que el trabajo que haría `next/image` ya está hecho — saltárselo con `unoptimized` para estas imágenes concretas no pierde nada. Las URLs externas pegadas a mano (`picsum.photos` en desarrollo) siguen pasando por el optimizador normal.
- **Si el proyecto necesitara escalar** (más tráfico, más VPS, o volver a repartir imágenes vía CDN), la migración de vuelta a un object storage tipo R2 es sencilla porque `uploadProductImage()` en `src/lib/storage.ts` es la única función a reemplazar — el resto del flujo (`ImageUploader`, la ruta `/api/admin/upload`, `parseImageUrls`) no depende de dónde vivan los archivos.
- **Toda imagen subida se reencoda a WebP en el servidor** (`sharp`, en `uploadProductImage()`), redimensionando el lado más largo a 1600px si hace falta — el formato de origen (JPEG/PNG/WebP/AVIF) no importa, siempre se guarda como `.webp`. No es solo por peso: reduce mucho el tamaño en disco (una imagen de cámara/móvil sin comprimir puede pesar varios MB) sin pérdida perceptible, ya que en la tienda nunca se muestran a tamaño completo. `sharp` ya venía como dependencia opcional de Next.js (lo usa para `next/image` en modo self-hosted); aquí se declara como dependencia directa porque el código de la app lo importa explícitamente.
- **Crear un producto autoguarda un borrador en `localStorage`** (`useFormDraft`, usado en `ProductForm`) — si falla la validación, caduca la sesión a media edición, o se cierra la pestaña sin querer, no se pierde lo ya rellenado (incluidas las imágenes ya subidas). Solo aplica al *crear*, no al *editar*: al editar, la fila de la BD ya hace de copia de seguridad, así que el riesgo real es mucho menor y no compensaba la complejidad de fusionar un borrador con datos ya guardados. El autoguardado escucha el evento `onChange` del `<form>`, salvo para las imágenes: `ImageUploader` actualiza un `<input type="hidden">` por código (React), lo que no dispara un `change` nativo, así que tiene su propio callback (`onUrlsChange`) para forzar el guardado del borrador cuando cambian las imágenes. El borrador se borra solo al guardar con éxito, o a mano con "Descartar y empezar de cero".
- **Borrar una imagen en el uploader la borra del disco, no solo de la lista del producto** — pero el *momento* del borrado depende de si la imagen ya estaba guardada en el producto o se subió en la misma sesión de edición, para que el admin no necesite FTP/SSH para limpiar archivos sueltos sin arriesgarse a dejar referencias rotas:
  - Imagen subida en esta misma edición (todavía no guardada en ningún producto): se borra del disco al momento (`DELETE /api/admin/upload` → `deleteProductImage()` en `src/lib/storage.ts`), es segura de borrar porque no está referenciada en ningún sitio.
  - Imagen que ya pertenecía al producto (venía en `defaultValue` del `ImageUploader`): el borrado del archivo se **aplaza hasta que el formulario se guarda con éxito**. El cliente la quita de la lista visible y la añade a un campo oculto (`imageUrls_deleted`); `updateProduct` (`src/lib/actions/admin/products.ts`) solo llama a `deleteProductImage()` para esas URLs *después* de que la transacción de Prisma haya terminado. Así, si se cancela la edición sin guardar, la imagen sigue intacta y el producto no se queda apuntando a un archivo borrado. **Esto reemplaza un primer intento (borrado inmediato siempre) que causó justo ese problema en producción** — quitar una imagen de un producto ya guardado sin darle a "Guardar" después dejaba el archivo borrado pero la URL seguía en `imageUrls`, dando 404 en la tienda.
  - En ambos casos hay confirmación (`window.confirm`) antes de nada, porque es una acción permanente e irreversible.
  - `deleteProductImage()` solo borra si el nombre de archivo coincide con el patrón `uuid.extensión` que generamos nosotros (regex en `storage.ts`); una URL externa pegada a mano o cualquier intento de path traversal (`../../algo`) no hace nada (`path.basename` + la regex lo neutralizan).
- **nginx limita el cuerpo de la petición a 1MB por defecto.** La subida de imágenes de producto (hasta 5MB antes de comprimir a WebP) necesita `client_max_body_size` más alto en el bloque de nginx del sitio (`deploy/store.bskully.es.conf` documenta el valor real, 10M) — sin esto, subir una foto de más de 1MB da un `413` que no pasa por el manejo de errores de la app (el navegador ni siquiera ve el mensaje de error de Next.js, porque nginx corta la petición antes de que llegue al contenedor). Si se añade otro endpoint que reciba archivos grandes, revisar este límite.
- **El checkout de PayPal se degrada con gracia** si `PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET` no están configurados: se muestra un aviso en vez de romper la página. Lo mismo aplica a cualquier integración externa nueva — que la ausencia de credenciales no tumbe la build ni la página.
- **La imagen Docker de producción no lleva el CLI de Prisma.** Usa `output: "standalone"` de Next.js, que solo copia lo estrictamente necesario para `next start`/`server.js` — no `prisma`, no `tsx`. Por eso `docker-compose.prod.yml` tiene un servicio `migrate` aparte (etapa `builder` del `Dockerfile`, con `node_modules` completo) solo para `prisma migrate deploy` / `db seed` puntuales; no intentar correr esos comandos dentro del contenedor `app`.
- **Cuando un deploy incluye una migración, `prisma migrate deploy` va ANTES de recrear el contenedor `app`, nunca después "cuando haya un rato".** Hubo una interrupción real de ~7h en producción (`TableDoesNotExist` en `ProductLike`) por desplegar primero el código nuevo (que ya consultaba la tabla `likes`) y dejar la migración para más tarde tras confirmación del usuario — cualquier ventana entre ambos pasos es tiempo con la home y las páginas de categoría dando 500. Orden correcto: 1) `git pull`, 2) rebuild + `docker compose run --rm migrate npx prisma migrate deploy` (aplica la migración con el código YA en el repo, contra el contenedor `app` todavía viejo, que no la necesita), 3) solo entonces `docker compose up -d --build app` para recrear `app` con el código nuevo. Si migración y deploy de `app` no pueden ir seguidos en el mismo momento por lo que sea, mejor esperar a poder hacer los dos juntos que desplegar el código a medias.
- **No lanzar dos builds de Docker pesados a la vez en esta VPS.** Se probó (dos `docker compose build` en paralelo, `app` + `migrate`) y la carga se disparó a load average ~67 con la RAM agotada (sin swap configurado) — el OOM killer llegó a matar un proceso dentro de `antitropic-server` (Cards, otro proyecto en la misma máquina), que se reinició solo sin pérdida de datos pero con un corte real. Los builds de `migrate` y `app` deben ir en secuencia, no en paralelo.
- **`NEXT_PUBLIC_PAYPAL_CLIENT_ID` tiene que llegar como build arg**, no solo como variable de entorno en runtime — Next.js inlinea las `NEXT_PUBLIC_*` en el bundle de cliente durante `next build`, que ocurre dentro de la imagen Docker. Ver `ARG`/`ENV` en el `Dockerfile` y `build.args` en `docker-compose.prod.yml`.
- **Despliegue en VPS compartido**: ver `deploy/RUNBOOK.md` y la memoria del agente `bskully-vps-infra` para el contexto completo (otros proyectos en la misma máquina, patrón de nginx, decisión de Postgres propio).
- **`User.passwordHash` es opcional (`String?`).** Las cuentas creadas por Google no tienen contraseña hasta que el usuario pide un reset. `authorize()` en `src/lib/auth.ts` rechaza el login por Credentials si `passwordHash` es `null` — no intentar `bcrypt.compare` contra `null`.
- **Alta de usuarios de Google se hace a mano en el callback `signIn`** (`src/lib/auth.ts`), no automáticamente por Auth.js: al usar sesiones JWT sin adapter de base de datos, Auth.js no persiste nada en `User` por su cuenta. El callback hace `upsert` por email y sobrescribe `user.id`/`user.role` con los de nuestra fila antes de que el callback `jwt` los meta en el token.
- **Recuperar contraseña**: token de un solo uso (`PasswordResetToken`, hash SHA-256 del token en BD, el token en claro solo va en la URL del email), expira en 1h, rate-limited tanto al pedirlo como al usarlo. El mensaje de "te hemos enviado un email" es siempre igual exista o no la cuenta, para no permitir enumerar usuarios.
- **Autocompletado de direcciones con Google Places** (`GoogleAddressAutocomplete`, usado en `AddressForm`): usa el `PlaceAutocompleteElement` nuevo (web component `gmp-place-autocomplete`), no la clase `google.maps.places.Autocomplete` clásica -- Google la cerró a clientes nuevos el 1 de marzo de 2025, así que la clásica no era una opción real aquí. Solo autocompleta: el widget de Google en sí no se envía en el formulario ni se estiliza a juego con el resto de la UI (viviría en su propio shadow DOM); al seleccionar una dirección, `onSelect` rellena por referencia (`ref.current.value = ...`) los `<Input>` normales de `AddressForm`, que son los que de verdad se envían. La carga del script (`@googlemaps/js-api-loader`, API funcional `setOptions`/`importLibrary`, no la `Loader` clase que está deprecada) es un singleton a nivel de módulo para no reinyectar el script si el componente se monta más de una vez. Degrada con gracia sin `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`: el componente devuelve `null` y el formulario funciona igual, solo sin el buscador.
- **Likes de producto (`ProductLike`) requieren cuenta, a propósito** -- decisión tomada con el usuario: un like anónimo (tipo carrito, en `localStorage`) sería trivial de falsear (borrar cookies y volver a votar) justo para el dato que decide qué aparece en el carrusel principal, y más complejo de fusionar si el visitante luego inicia sesión. `toggleLike()` (`src/lib/actions/likes.ts`) llama a `requireUser()` (cualquier cliente logueado, no hace falta ser `ADMIN`), que redirige a `/login` si no hay sesión -- `LikeButton` no comprueba la sesión por su cuenta, deja que el redirect del server action se encargue.
- **El carrusel principal (`HeroCarousel`, en la home) prioriza los productos con más likes, y de forma natural va rellenando con los más recientes** mientras no haya likes todavía: `getFeaturedProducts()` ordena por `{ likes: { _count: "desc" } }` y luego por `createdAt: "desc"` como segundo criterio -- como todos los productos nuevos empatan a 0 likes, ese segundo criterio es lo que hace que el carrusel muestre "los últimos productos añadidos" de salida, sin necesitar una lista separada. Cuando un producto empieza a acumular likes, sube solo en el orden.
- **`HeroCarousel` separa la zona clicable (la imagen, envuelta en un `Link`) del botón "Comprar"** (fuera del `Link`, no dentro) -- meter el botón dentro del enlace habría disparado la navegación al detalle Y el añadido al carrito en el mismo clic, sin forma limpia de distinguir cuál quería el usuario. `LikeButton` sí puede vivir dentro del `Link` porque ya hace `preventDefault`/`stopPropagation` en su propio `onClick` (lo necesitaba igualmente para `ProductCard`, donde en teoría no hay enlace envolvente pero es una guarda barata).
- **`Input`/`Textarea` (`src/components/ui/`) no reenviaban `ref` a propósito hasta que hizo falta aquí**: son componentes de función normales que no declaraban `ref` como parámetro, y en React 19 eso significa que se descarta (ya no hace falta `forwardRef`, pero sigue habiendo que nombrar `ref` explícitamente para recibirlo). Sin este cambio, `ref={line1Ref}` en `AddressForm` se habría quedado siempre en `null`, un bug silencioso -- ni error de tipos ni de consola. Si se necesita ref en otro componente de `ui/` que no lo declare, aplica el mismo arreglo (añadir `ref` a la desestructuración de props y pasarlo al primitivo de Base UI).
- **Email transaccional por SMTP se degrada igual que PayPal**: sin `SMTP_HOST`/`SMTP_USER`/`SMTP_PASSWORD`, `sendPasswordResetEmail`/`sendOrderConfirmationEmail` (`src/lib/email.ts`, nodemailer) solo imprimen por consola en vez de fallar — útil en desarrollo. Se usa el buzón de correo real de `bskully.es` (buzondecorreo.com) en vez de un servicio tipo Resend/SendGrid, porque ya existía esa infraestructura de correo y evita verificar un dominio nuevo.
- **El email de confirmación de pedido se envía desde `captureOrder()` (`src/lib/actions/checkout.ts`), envuelto en try/catch, después de capturar el pago y descontar stock** -- un fallo al enviarlo (SMTP caído, lo que sea) se registra en el servidor pero nunca revierte ni bloquea la confirmación del pedido al cliente; el pago ya está hecho, eso no puede depender de que salga un email. Usa los datos ya guardados en `OrderItem` (`nameSnapshot`/`unitPriceCents`, snapshot en el momento de la compra) y `Order.addressSnapshot`, no relee `Product` -- así el email siempre refleja lo que el cliente realmente pagó, aunque el producto cambie de precio o se borre después.
- **Las categorías sin ningún producto activo se ocultan solas** (`getTopLevelCategories()`, filtro `products: { some: { isActive: true } }`) — no tiene sentido enlazar a una categoría vacía desde el header o la home. Reaparecen automáticamente en cuanto tengan al menos un producto activo, sin tocar nada más. Esto **no** afecta al panel de admin (`/admin/categorias` usa su propia consulta, sin este filtro) ni bloquea el acceso directo a `/categoria/<slug>` si alguien tiene el enlace — solo deja de *anunciarse* en la navegación.
- **Las páginas legales (`/aviso-legal`, `/privacidad`, `/cookies`, `/terminos`) tienen datos reales del titular** (persona física/autónomo: nombre, NIF, domicilio, email de contacto -- todo vía `siteConfig`). Son datos con responsabilidad legal real (LSSI-CE/RGPD); conviene revisar el contenido con un profesional antes de asumir que cubre el cumplimiento normativo real de la tienda. La política de cookies ya refleja que hay cookies técnicas (siempre activas) y de analítica (Google Analytics, solo si se acepta el aviso) -- si se añade publicidad/remarketing en el futuro, hay que volver a actualizarla.
- **Google Analytics 4 solo se carga tras consentimiento explícito** (`CookieConsentBanner`, `src/app/layout.tsx`): sin `NEXT_PUBLIC_GA_MEASUREMENT_ID` no aparece ni el aviso ni se inyecta el script -- mismo criterio de degradación que el resto de integraciones externas. La decisión (aceptar/rechazar) se guarda en `localStorage` (`skullystore-cookie-consent`); el enlace "Preferencias de cookies" del footer la borra y dispara un evento (`skullystore:cookie-consent-reset`) para volver a mostrar el banner sin recargar. `trackEvent()` (`src/lib/analytics.ts`) es un no-op si `window.gtag` no existe (sin consentimiento, o GA no configurado), así que las llamadas a eventos de ecommerce (`view_item` en `ProductDetailModal`, `add_to_cart` en `AddToCartButton`, `begin_checkout` en `CartDrawer`, `purchase` en la página de confirmación vía `PurchaseTracker`) son seguras de dejar siempre en el código. El evento `purchase` lleva `transaction_id: order.id` para que GA4 deduplique si se recarga la página de confirmación, y solo se dispara si `order.status === "PAID"`. Como `NEXT_PUBLIC_GA_MEASUREMENT_ID` se inlinea en el bundle de cliente durante el build, tiene que llegar como build arg además de variable de entorno (mismo patrón que `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` -- ver `ARG`/`ENV` en el `Dockerfile` y `build.args` en `docker-compose.prod.yml`).
- **`Product` tiene `weightGrams`/`lengthCm`/`widthCm`/`heightCm`, todos opcionales y sin usar en ningún cálculo todavía** — es solo para ir guardando el dato producto a producto, de cara a calcular gastos de envío por peso/dimensiones y destino más adelante (pendiente de decidir el modelo de cálculo). No confundir con el backlog de "gastos de envío en el checkout", que sigue sin implementarse.
- **`Product.vatCents`/`shippingCostCents` son un desglose puramente informativo**, editado a mano por el admin en el formulario de producto ("IVA incluido"/"Envío incluido"). `priceCents` sigue siendo el único precio final real que paga el cliente — estos dos campos no se leen en ningún punto del checkout, son solo para que el admin sepa cuánto de ese precio final es impuesto y cuánto es envío. No confundir con `weightGrams`/etc. (de cara a un cálculo futuro) ni con el backlog de gastos de envío reales en el checkout.
- **`StockNotificationRequest` (aviso de "¿te avisamos cuando repongan stock?") no exige cuenta, a propósito** -- a diferencia de `ProductLike`, aquí no hay ranking ni dato que se pueda falsear con valor real: es solo un email de contacto que se reenvía al admin, así que exigir login solo añadiría fricción sin beneficio. El `@@unique([productId, email])` evita reavisar al admin si la misma persona repite el envío para el mismo producto -- `requestStockNotification()` (`src/lib/actions/stock-notifications.ts`) comprueba primero si ya existe antes de crear y enviar el email, y devuelve el mismo mensaje de éxito en ambos casos (no hay nada que delatar, pero mantiene la respuesta simple).
- **`sendStockNotificationRequestEmail`/`sendNewOrderAdminNotification` (`src/lib/email.ts`) van a `ADMIN_NOTIFICATION_EMAIL`**, con `juan@dalebrook.org` como valor por defecto si no está definida -- mismo criterio de degradación que el resto del correo transaccional (sin SMTP configurado, se registran en consola en vez de enviarse) y el mismo patrón de try/catch no bloqueante ya usado para `sendOrderConfirmationEmail`: un fallo al avisar al admin no debe romper ni el pedido ya pagado ni la petición de aviso de stock del visitante. El enlace del email de stock apunta a `/admin/productos/<id>` (edición en el admin), no a una URL pública del producto -- no hay una URL pública fiable a un producto suelto fuera del contexto de su categoría o del carrusel de destacados.
- **El recordatorio de likes es deliberadamente de disparo manual, no un cron** -- a diferencia de todo el correo anterior (transaccional: confirmación de pedido, recuperar contraseña, avisos al admin), este es email comercial dirigido al cliente ("le diste like, sigue disponible"), y en España eso requiere consentimiento explícito (LSSI-CE) que todavía no se ha resuelto con alguien con conocimiento legal -- ver ROADMAP.md → Backlog. Por eso no hay ninguna tarea programada en el VPS que lo ejecute solo; alguien tiene que lanzarlo a mano, por terminal (`npx tsx -r dotenv/config scripts/send-like-reminders.ts --dry-run`) o desde `/admin/recordatorios` (casilla "solo previsualizar" marcada por defecto). La lógica vive una sola vez en `runLikeReminders()` (`src/lib/like-reminders.ts`) para que ambas vías de disparo se comporten igual -- el script CLI y la Server Action de admin (`sendLikeRemindersAction`, admin-only vía `requireAdmin()`) son envoltorios finos sobre esa función. `ProductLike.reminderSentAt` marca los que ya se avisaron para no repetir, y se salta a quien ya compró el producto (`OrderItem` del mismo usuario/producto) aunque no se le haya avisado todavía. Mismo motivo por el que un recordatorio de "carrito abandonado" no existe todavía: el carrito vive solo en `localStorage` hasta que se llega a checkout (ver más abajo), así que el servidor no tiene visibilidad de un carrito que nunca se sincronizó -- no hay a quién avisar, ni con qué email.
- **Sin stock bloquea el botón "Comprar" en el cliente**: `AddToCartButton` acepta `outOfStock`, y `ProductCard`/`ProductDetailModal`/`HeroCarousel` se lo pasan como `product.stock <= 0` — las tres vistas que renderizan el botón. Es solo una barrera de UX (evita el intento obvio); la validación real y vinculante sigue siendo la de servidor en `createOrderFromCart` (ver más abajo, "Precios y stock nunca se confían del cliente").
- **Los iconos ya no son de `lucide-react`, son propios** (`src/components/icons/`, generados por `scripts/extract-icons.ts` a partir de `public/iconos.svg`, la hoja con los 21 iconos dibujados a mano por el usuario). Cada componente es un `<svg fill="currentColor">` con el mismo nombre que su equivalente lucide (`HeartIcon`, `XIcon`, `Grid2x2Icon`...) para que el import sea un cambio de una línea en cada sitio -- misma firma de props (`React.SVGProps<SVGSVGElement>`), mismo `className` por defecto (`size-4`), así que el recoloreo por CSS (hover de cabecera/carrito, `fill-current` en `LikeButton`, los colores verde/rojo/ámbar de los toasts) sigue funcionando igual que con lucide. Excepción: el icono de "bolsa" (`ShoppingBagIcon`, fiel al nombre real de lucide) se generó pero no se usa en ningún sitio -- el botón del carrito en la cabecera usa `ShoppingCartIcon` (el dibujo del carrito con ruedas), decisión tomada con el usuario porque su hoja de referencia traía ambos dibujos por separado. `lucide-react` sigue como dependencia (declarado en `components.json` → `iconLibrary`, por si un futuro `npx shadcn add` lo necesita) pero ya no lo importa nada del código de la app -- si se regenera `iconos.svg` desde cero, el mapeo de qué trazo pertenece a qué icono (`ICONS` en `extract-icons.ts`, por orden de aparición en el documento) hay que rehacerlo a mano comparando con la cuadrícula de referencia.

## Seguridad

- **Cabeceras HTTP** (`next.config.ts`): CSP, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security`. La CSP es **estática, sin nonces**: usar nonces exigiría verificar en un navegador real que la hidratación de Next sigue funcionando (no se puede comprobar solo con `curl`), así que se ha optado por la versión más segura que sí se puede verificar. `style-src` incluye `'unsafe-inline'` porque los colores de acento por producto usan `style` inline (`accentColor` en `ProductCard`/`Badge`) — es un riesgo bajo (datos del propio admin, no de usuarios) y cambiarlo implicaría rehacer ese sistema. Si en algún momento se puede probar en navegador, migrar a CSP con nonces vía `proxy.ts` (ver la guía de Next en `node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`).
- **Rate limiting de login**: en `authorize()` (`src/lib/auth.ts`), no en la Server Action de login. Es importante que esté ahí y no en `src/lib/actions/auth.ts`: `authorize()` es el único punto por el que pasa *cualquier* intento de login, venga del formulario o de un POST directo a `/api/auth/callback/credentials` (el segundo caso se probó explícitamente — ver historial de commits). Implementación en memoria (`src/lib/rate-limit.ts`), suficiente para un solo proceso/VPS; si se despliegan varias instancias, pasar a un almacén compartido.
- **`createOrderFromCart`/`captureOrder` (`src/lib/actions/checkout.ts`) tienen rate limit por usuario** (`checkout-create:<userId>`/`checkout-capture:<userId>`, 10 por 15 min) -- a diferencia de login/registro/recuperar contraseña, esto se detectó tarde (revisión de seguridad externa) porque exige estar autenticado, lo que reduce el riesgo real pero no lo elimina.
- **Webhook de PayPal (`src/app/api/paypal/webhook/route.ts`) como red de seguridad, no como vía principal**: el checkout sigue confiando en la captura síncrona (`capturePayPalOrder()`, iniciada desde el navegador en el callback `onApprove` del SDK) como flujo normal. El webhook solo existe por si esa respuesta nunca llega al servidor (corte de red, pestaña cerrada justo después de pagar) mientras PayPal sí completó el cobro de verdad -- sin el webhook, ese pedido se quedaría como "no pagado" para siempre aunque el cliente haya pagado. Verifica la firma con la API de PayPal (`verifyPayPalWebhookSignature()` en `src/lib/paypal.ts`) antes de confiar en nada del payload -- sin `PAYPAL_WEBHOOK_ID` configurada, responde 503 y no hace nada (el checkout normal no depende de esto). La lógica de "marcar pagado, descontar stock, mandar emails" está en `fulfillPaidOrder()` (`src/lib/order-fulfillment.ts`), compartida entre `captureOrder()` y el webhook, y es **idempotente a propósito**: usa un `updateMany` con `status: { not: "PAID" }` como guarda atómica, así que si las dos vías llegan a marcar el mismo pedido casi a la vez (o PayPal reenvía el mismo evento de webhook duplicado, algo que hace de verdad en producción), solo la primera aplica el descuento de stock y envía los emails -- la segunda ve `count === 0` y no hace nada más.
- **Contraseñas**: mínimo 10 caracteres + letra + número (`SignupSchema` en `src/lib/actions/auth.ts`), hash con bcrypt coste 12.
- **Precios y stock nunca se confían del cliente**: el checkout siempre relee `Product.priceCents` de la base de datos al crear el `Order` (`src/lib/actions/checkout.ts`), nunca usa lo que mande el navegador. El stock **se valida** en `createOrderFromCart()` (comparando `item.quantity` contra `product.stock` justo antes de crear el pedido) -- antes de esto no se validaba en ningún punto del ciclo, así que se podía comprar más unidades de las que había en stock sin ningún aviso, y `captureOrder()` podía dejar el stock en negativo. El carrito (`localStorage`, `CartProvider`) sigue sin tener ninguna noción de stock disponible -- se puede añadir cualquier cantidad ahí sin aviso; el punto real de corte es el checkout, no el carrito.
- **`createOrderFromCart`/`captureOrder` (`src/lib/actions/checkout.ts`) devuelven `{ error }` en vez de lanzar** -- se invocan directamente desde `PayPalCheckoutButtons` (no vía `useActionState`/formulario), y un `throw` desde una Server Action se oculta igual en producción se invoque como se invoque; devolver el error como valor normal es lo único que garantiza que `setError()` en el cliente reciba el mensaje real (carrito vacío, dirección inválida, sin stock...) en vez de un fallback genérico. Los fallos que vienen de la propia API de PayPal (`src/lib/paypal.ts`) sí se dejan como `throw` sin capturar -- ahí el mensaje genérico de `onError` en `PayPalCheckoutButtons` es apropiado, no hay nada más específico que explicarle al cliente.
- **`next-auth` sigue en beta (v5)**: es la versión estable de facto para App Router y ampliamente usada en producción, pero al ser una tienda con pagos merece la pena vigilar el lanzamiento de la v5 estable y actualizar cuando salga.
- **Páginas legales (`/aviso-legal`, `/privacidad`, `/cookies`, `/terminos`) llevan `robots: { index: false, follow: false }`** en su `metadata`, pero `src/app/robots.ts` **no** las incluye en `Disallow`. Es a propósito y en ese orden: si un `Disallow` le impide a Googlebot rastrear la página, tampoco llega a ver la etiqueta `noindex` -- la URL puede seguir apareciendo en resultados de búsqueda (sin snippet) si algo enlaza a ella. Dejar que el crawler la lea y respete el `noindex` es la única forma de garantizar que el NIF/domicilio del titular no acaben cacheados por un buscador. `robots.ts` sí bloquea con `Disallow` un puñado de bots de scraping SEO/comercial conocidos (Ahrefs, Semrush, MJ12, etc.) que no tienen ningún motivo legítimo para volcar el sitio, más `/admin` y `/api/` para cualquier bot.
- **nginx aplica `limit_req` (10 r/s, ráfaga 20) a todo `store.bskully.es`** (`deploy/store.bskully.es.conf`), como capa extra frente a crawling agresivo/scraping y probing automatizado, complementaria al rate limit ya existente a nivel de aplicación en login/checkout (arriba). `limit_req_zone` vive fuera de cualquier `server {}` en ese archivo porque solo es válido en el contexto `http {}` de nginx, y el `include` de sites-enabled cae ahí.
- `npm audit` se mantiene en 0 vulnerabilidades vía `overrides` en `package.json` (postcss/@hono-node-server son dependencias internas de Next/Prisma, no directas). Revisar `npm audit` periódicamente — los `overrides` fuerzan versiones que no son las que Next/Prisma declaran por defecto.

## Cómo se verifica cada cambio

El navegador de este entorno de trabajo tiene bloqueado `localhost` por política de la organización, así que la verificación de UI se hace así:

1. `npm run build` — build limpio, sin errores de tipos.
2. Servidor de desarrollo en background (`npm run dev`) + `curl` a las rutas afectadas, comprobando el HTML devuelto y el log del servidor (sin warnings/errores).
3. Para flujos que dependen de JS de cliente o de Server Actions con protocolo RSC (formularios con `useActionState`, añadir al carrito, etc.), no se puede automatizar por curl de forma fiable — se han validado por revisión de código + patrones estándar de Next.js, y conviene probarlos a mano en el navegador tras cambios grandes.
4. Para probar flujos autenticados sin navegador: el login por Credentials de Auth.js sí admite un POST normal (`/api/auth/csrf` + `/api/auth/callback/credentials`), a diferencia de los Server Actions. Ver `scripts/seed-test-user.ts` para generar datos de prueba.
5. El log del servidor de desarrollo a veces muestra mensajes `[browser] ...` — son avisos de consola reenviados desde un navegador real que tenga la app abierta (el del usuario, no el del agente). Si aparece un warning de React/Base UI que no tiene pinta de estar relacionado con el último cambio, reiniciar `npm run dev` limpio antes de investigarlo a fondo: se ha visto al menos un caso de un aviso de "controlled/uncontrolled" que era puro artefacto de Fast Refresh tras varias ediciones seguidas de un componente con estado, y desapareció con un reinicio limpio.

## Flujo de trabajo

- El desarrollo va **fase a fase** (ver ROADMAP.md): cada fase debe quedar en un estado comprobable antes de pasar a la siguiente, no se acumulan varias fases sin verificar.
- Copys de interfaz en **español**, código/identificadores en inglés (convención habitual, no hay una regla estricta escrita en ningún sitio más que aquí).
- No añadir abstracciones, capas o configuración para necesidades hipotéticas — este proyecto es intencionadamente pequeño (poco tráfico, un solo mantenedor). Preferir la solución directa.
- Antes de dar por buena una integración externa nueva (pasarela de pago, almacenamiento, email...), confirmar si ya hay credenciales/cuenta creada; si no, construir la integración igualmente pero con degradación visible en vez de bloquear el desarrollo.
